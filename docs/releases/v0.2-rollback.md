# NYUSH Course Planner v0.2 Rollback Runbook

This runbook restores service without deleting immutable catalog captures, normalized snapshots, correction events, overlays, or student plans.

## Rollback triggers

Start rollback for any of the following:

- catalog corruption, incomplete 14-source membership, or a source anomaly that reached the active release;
- migration behavior that loses or mutates user, session, plan, catalog, correction, or overlay data;
- authentication, authorization, or privacy breach;
- an unusable critical planning, synchronization, or correction flow; or
- a sustained error-rate or performance regression that materially blocks normal planning.

## Before changing state

1. Stop new catalog publication and record the incident time, app commit, active release ID, previous release ID, database identifier, and diagnostics.
2. Preserve logs and database snapshots according to the operator's access policy. Do not copy plan or report text into general logs.
3. Confirm the selected prior app build and catalog release were previously healthy.

## Application rollback

1. Route traffic to the last known-good application artifact or commit using the hosting platform's normal atomic rollback.
2. Keep the database at the migrated schema unless a separately reviewed forward-fix is required. v2 plan rows and v1 backup/export data remain stored.
3. Do not run destructive down migrations and do not delete correction or overlay tables.

## Catalog release rollback

Within one database transaction and under the release-composition lock:

1. lock the catalog release pointer;
2. verify the target release is complete and references a healthy or explicitly retained snapshot for every configured source;
3. retire the problematic active pointer and activate the previous composed release pointer;
4. commit once, then invalidate catalog read caches; and
5. retain the problematic release, snapshots, diagnostics, captures, corrections, events, and overlays for investigation.

Never rebuild the previous release by copying rows. Reactivate its existing immutable composition.

## Plan and correction compatibility

- v2 plan rows, optimistic revisions, conflict snapshots, and v1 migration backups remain available to both the current and prior compatible app build.
- If an older build cannot interpret a v2 field, prefer a compatible hotfix or read-only maintenance mode; never coerce or discard the stored plan.
- Correction requests, messages, notifications, immutable events, typed overlays, and release reconciliation results are retained even when the visible catalog pointer moves backward.

## Verification after rollback

1. Confirm the prior app build and expected catalog release ID are served.
2. Verify one anonymous catalog query, one signed-in plan load/save, owner scoping, admin denial, and one prior correction timeline.
3. Verify Shanghai programs and all 13 New York source memberships remain present, with no New York degree programs.
4. Verify a v2 plan and its v1 backup/export path remain readable.
5. Record response errors, payload identifiers, source diagnostics, and the exact rollback transaction outcome in the incident record.

Do not declare recovery until the original trigger is no longer observable and no immutable or user-owned data was removed.
